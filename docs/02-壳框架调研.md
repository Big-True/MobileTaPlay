# MobileTaPlay — 跨平台壳框架调研

> 对应需求分析待决项 #3；产品名已定为 **MobileTaPlay**  
> 约束回顾：纯第三方客户端 · 不做登录 · 仅加载在线游戏 · 手柄 + 触屏  
> **平台优先级（现行）：Android → iOS → Win → macOS/Linux**（桌面优先旧序见 §14）  
> 本文只做技术选型分析，不进入实现

---

## 1. 选型要回答什么

MobileTaPlay 本质是 **「远程网页壳 + 输入桥」**。壳框架只要把这四件事做好即可：

| # | 能力 | 为什么关键 |
|---|---|---|
| A | **稳定加载** `https://h5mota.com/play/` 等远程 URL | 主内容不在本地 |
| B | **向页面注入脚本**（Input Bridge） | 引擎无 Gamepad API，必须把手柄翻译成 keyCode/触点 |
| C | **手柄可达** | Gamepad API 或原生 HID → 合成事件 |
| D | **触屏/窗口/全屏** | 移动 + 桌面体验 |

v1 明确 **不做**：登录 UI、离线包、造塔器。这会让选型明显偏向「WebView 壳」，而不是完整跨端 UI 框架。

---

## 2. 候选方案总览

| 方案 | 本质 | 覆盖端 | 手柄路径 |
|---|---|---|---|
| **A. Electron** | 自带 Chromium | Win/mac/Linux（官方无移动） | Chromium Gamepad API，最稳 |
| **B. Tauri 2** | 系统 WebView + Rust | Win/mac/Linux/Android/iOS | WebView Gamepad / 需原生补强 |
| **C. Capacitor** | 系统 WebView（移动优先） | iOS/Android/桌面(社区) | 同上，移动强、桌面弱 |
| **D. Flutter + webview_flutter** | Flutter UI + 系统 WebView | 全端 | 插件生态一般，WebView 内靠 Gamepad |
| **E. React Native + WebView** | RN 壳 | iOS/Android（桌面弱） | 需原生模块，碎片多 |
| **F. 原生分端**（Kotlin / Swift / WinUI） | 每端一个壳 | 全端 | 原生 GameController / HID 最强 |
| **G. PWA / 浏览器** | 无壳 | 浏览器 | 已可用，但非「App」定位 |

> 移动端优先后，决赛圈变为 **C / B / D**（Capacitor / Tauri 2 / Flutter）；Electron 退居桌面补件；A 不再适合当主壳。

## 4. 关键技术事实（调研摘要）

### 4.1 Gamepad API 现状

来源：MDN / caniuse（2026）

| 环境 | Gamepad API |
|---|---|
| Chrome / Edge / Electron（Chromium） | ✅ 完整 |
| Safari macOS / iOS 10.3+ | ✅ 基本可用 |
| Chrome Android WebView（现代） | ✅ 通常可用 |
| Firefox | ✅（需页面可见/交互后暴露） |
| Opera Mini / 旧 Android Browser | ❌ |

全球支持约 **97%**。  
但 **「浏览器支持」≠「WebView 壳内稳定」**：

- **Electron = Chromium**：Gamepad、KeyboardEvent、Canvas 行为与 Chrome 一致，**输入桥最容易写对**。
- **Tauri / Capacitor / Flutter WebView = 系统 WebView**：
  - Windows → **WebView2（Chromium）**，Gamepad 接近 Chrome；
  - macOS/iOS → **WKWebView**，Gamepad 可用，但外接手柄在 iOS 上历史上偏脆，可能要走 **原生 GameController → 注入合成键事件**；
  - Android → **Android System WebView（Chromium）**，外接手柄多数可被 Gamepad API 看到；
  - Linux → **WebKitGTK**，Gamepad 支持不一，需实测。

### 4.2 远程页脚本注入（Input Bridge 命门）

| 框架 | 远程 URL | 注入方式 | 评价 |
|---|---|---|---|
| Electron | 一等公民 | `webContents.executeJavaScript` / preload / 拦截响应插 script | ★★★★★ |
| Tauri 2 | 支持 Brownfield 远程页 | `initialization_script` / `eval` | ★★★★☆（需配置外链、CSP） |
| Capacitor | 通常包本地资源；远程需自定义 | iOS `WKUserScript`、Android `evaluateJavascript` | ★★★☆（要写原生插件） |
| Flutter webview | 支持 URL | `addJavaScriptChannel` / `runJavaScript` / user scripts | ★★★☆ |
| RN WebView | 支持 | `injectedJavaScript` / `injectedJavaScriptBeforeContentLoaded` | ★★★☆ |

> 结论：**Electron / Tauri 对「注入到第三方站点」路径最短**；移动 WebView 方案都要补一层原生注入 API。

### 4.3 Canvas 2D（mota-js）

mota-js：HTML5 Canvas，大量 32px 图块、动画、缩放、横竖屏。

| 载体 | 表现 |
|---|---|
| Chromium（Electron / WebView2） | 与 Chrome 一致，基线最好 |
| WKWebView | 通常够用；注意离屏/缩放与 GPU 合成 |
| Android WebView | 够用；低端机看 WebView 版本 |
| Flutter 自绘 | **不适用**——游戏在 WebView 内，不走 Flutter 渲染 |

壳框架 **不改变** Canvas 实现，只改变 WebView 内核；**Electron 统一 Chromium = 行为最少意外**。

### 4.4 平台矩阵

| | Windows | Android | macOS | Linux | iOS |
|---|---|---|---|---|---|
| Electron | ★★★★★ | ❌（无官方） | ★★★★★ | ★★★★ | ❌ |
| Tauri 2 | ★★★★★ | ★★★★（移动已 GA） | ★★★★★ | ★★★★ | ★★★★ |
| Capacitor | ★★（社区桌面） | ★★★★★ | ★★ | ★★ | ★★★★★ |
| Flutter | ★★★★ | ★★★★★ | ★★★★ | ★★★ | ★★★★ |
| RN | ★★ | ★★★★ | ★★ | ★★ | ★★★★ |

与优先级 **Win → Android → macOS/Linux → iOS** 对齐度：

- **Tauri 2**：五端都在官方路径上，与优先级最贴。
- **Electron + Capacitor 双栈**：Win/mac/Linux 用 Electron，Android/iOS 用 Capacitor——移动与桌面输入桥逻辑可共享 TS，但 **两套壳工程**。
- **Flutter**：一码五端，但远程 WebView 注入与手柄仍要各端原生补丁，省 UI 壳不省输入桥。

### 4.5 包体与资源

| | 典型安装包 | 备注 |

MobileTaPlay 只是网页壳，**包体敏感度中等**；手柄玩家更在意稳定性。

## 5. 分方案深评

### 5.1 Electron

**优点**

- Chromium 内核：Gamepad、键盘、Canvas 与 Chrome 一致，**输入桥单测成本最低**。
- 远程 URL、`session`、权限、HID/USB、自动更新、崩溃报告都是成熟 API。
- 文档/资料/中文社区极多；Windows 发行链路（NSIS/Squirrel）简单。
- 无官方移动 → 不会在移动端被 Electron 拖累。

**缺点**

- **没有官方 Android/iOS**：Android 阶段必须换/叠第二方案。
- 包体大、内存高（对纯壳偏奢侈）。
- 手柄若走 Chromium Gamepad，Win 上很稳；若以后要「Steam Deck 式」原生手柄细节（陀螺仪、灯效），仍要原生插件。

**适合 MobileTaPlay 的点**：M1/M2（Windows 桌面 + 手柄）最快落地。

### 5.2 Tauri 2

**优点**

- 一码 Win/Android/macOS/Linux/iOS，与产品优先级自然对齐。
- 体积小、安全模型（capabilities）清晰；`initialization_script` 可注入 Input Bridge。
- 插件：updater、store、shell、haptics 等覆盖壳层需求。
- 远程 Brownfield 模式就是为「已有网站」准备的。

**缺点**

- **系统 WebView 碎片**：Win=WebView2 还好，Linux=WebKitGTK、iOS=WKWebView 的 Gamepad 需实测；iOS 外接手柄可能要 **Rust/移动原生插件** 转发。
- 移动工程（Android/iOS）比纯桌面多一截配置（SDK、签名、权限）。
- 用 Rust 做 IPC/插件对纯前端团队有学习曲线（若只写 TS 前端 + 少量插件则可控）。
- WebView2 依赖：Win 上老系统可能要装 Runtime（可静态链）。

**适合 MobileTaPlay 的点**：若希望 **单一技术栈覆盖五端**，这是最完整答案。

### 5.3 Capacitor

**优点**

- 移动 WebView 容器极其成熟（Ionic 出身），游戏/Canvas 指南齐全。
- Android 优先路径顺：打包、签名、Play 侧载都熟。
- 与 Web 技能贴合，插件写 Swift/Kotlin 门槛低于 Rust。

**缺点**

- **桌面是弱项**：Windows 第一优先级却不是 Capacitor 主战场。
- 远程站点不是默认场景（默认加载 `www` 本地资源）；要包「打开 h5mota」需自定义原生壳 + 注入。
- 手柄在 iOS/Android WebView 内同样受系统限制。

**适合**：若产品改以「Android/iOS 为主」会更强；与当前优先级 **倒挂**。

### 5.4 Flutter / RN

- 共同问题：UI 层很强，但 **远程 WebView + 手柄输入桥** 仍是二级公民，要写不少原生代码。
- Flutter 桌面 + 移动统一好看，但 WebView 插件能力不如直接用 Tauri/Electron 壳。
- RN 桌面生态弱，不符合 Win 优先。

**结论**：对 MobileTaPlay 是「用错层」——我们不需要漂亮原生 UI，需要的是 **好的 WebView 与输入注入**。

### 5.5 原生分端（对照）

| | 说明 |
|---|---|
| 优点 | iOS GameController、Android KeyEvent、Windows XInput/GameInput 控制力最强 |
| 缺点 | 三套代码、三套 CI、迭代慢 |
| 何时回头 | 若 WebView 手柄在 iOS 实在不可救，可 **仅 iOS 原生壳**，其余保持 Web 壳 |

### 5.6 PWA

- 零安装，Win/Android 浏览器已可玩。
- 不能当正式「App」交付（图标、手柄映射 UI、设置持久化受限）。
- 可作 **附加渠道**，不作为主壳。

## 7. 推荐结论（给 MobileTaPlay · 移动端优先）

> 优先级 **Android → iOS → Win → macOS/Linux** 会 **翻转主推荐**。

### 7.1 首选：**Capacitor（Android/iOS）+ 桌面后补**

**理由：**

1. 前两端就是 **Android / iOS**——Capacitor 的主场；打包、签名、侧载/商店路径成熟；
2. 移动 WebView 容器（游戏/Canvas 指南）文档齐，和 mota-js 这类 Canvas 游戏同场景；
3. 官方 `H5mota-Android` 就是 Kotlin WebView，证明「Android 壳包 h5mota」路线成立；Capacitor 是它的 Web 化超集；
4. 触屏成为主输入后，Capacitor/Ionic 的安全区、横竖屏、沉浸式经验更贴；
5. Win 在第 3 位——可后补，不必拖累 M1/M2。

**桌面后补怎么补（M3）：**

| 选项 | 说明 |
|---|---|
| **Tauri 2 桌面**（推荐） | 复用同一套 Input Bridge TS；Win 用 WebView2 |
| Electron 桌面 | 若 Win 手柄要绝对稳，可临时用 Electron |
| Capacitor 桌面 | 不推荐当 Win 主力（社区向） |

**结构：**

```
packages/input-mapping   # 共享 TS：映射表、键码、死区
packages/input-bridge    # 共享 TS：Gamepad/触控 → keyCode / touch
packages/shell-common    # 注入、设置 schema、错误页
app-mobile  (Capacitor)  # M1 Android / M2 iOS
app-desktop (Tauri 2)    # M3 Win / M4 macOS·Linux
```

**必须提前做的验证（移动优先闸门）：**

| 验证项 | 通过标准 | 平台 | 时机 |
|---|---|---|---|
| V1 | 打开 `/play/`，进塔，Canvas/触屏正常 | Android | 第一周 |
| V2 | 注入 Input Bridge，虚拟键驱动移动 | Android | 第一周 |
| V3 | 蓝牙手柄 Gamepad API 或 KeyEvent 转发 | Android | 第二周 |
| V4 | WKWebView 加载 + 注入 + 触屏 | iOS | M2 初 |
| V5 | iOS 外接手柄：Gamepad 或 GameController 插件 | iOS | M2 |
| V6 | 安全区/刘海/手势条不抢触控 | Android+iOS | M1–M2 |
| V7 | Win 键盘 + 手柄（Tauri WebView2） | Win | M3 |
| V8 | Linux/macOS 抽测 | 桌面 | M4 |

若 **V3/V5 手柄失败**：保留触屏为主交付，手柄标为「实验」；或 iOS 仅做 GameController 原生插件。

### 7.2 备选：**Tauri 2 单壳五端**（要单仓单构建时）

**何时选它而不是 Capacitor 优先：**

- 强烈希望 **只维护一个壳工程**；
- 能接受 Tauri 移动（Android/iOS）成熟度低于 Capacitor 的风险；
- 团队愿意写少量 Rust 插件（尤其 iOS GameController）。

验证顺序改为：**Android → iOS → Win → Linux**，而不是先啃 Windows。

### 7.3 明确不选（v1 · 移动序）

| 方案 | 原因 |
|---|---|
| **Electron 主壳** | 无官方 Android/iOS，与前两端优先级直接冲突 |
| RN 主壳 | iOS/桌面手柄与远程注入碎片多，性价比低 |
| 纯原生三端 | 超出第三方客户端成本 |
| 只做 PWA | 达不到可配置手柄 + 正式 App 交付 |

### 7.4 Flutter 为何只差半档

移动优先下 Flutter（全端、触屏好）**进入决赛圈**，但仍弱在：

1. 远程第三方页不是默认场景，`webview_flutter` 注入要自己包；
2. 手柄插件生态不如「Web Gamepad + 原生兜底」直观；
3. 对「网页壳」来说仍多一层 UI 框架。

若团队已是 Flutter 重度用户，可升为主选；否则 Capacitor/Tauri 更对口。

## 8. 与 MobileTaPlay 架构的落地映射

无论 Capacitor + Tauri 或 Tauri 单壳，**分层不变**：

```
┌─────────────────────────────────────────────┐
│  Shell                                      │
│  · Capacitor (Android/iOS)                  │
│  · Tauri 2 (Win/mac/Linux)                  │
│  · 安全区 / 沉浸式 / 横竖屏 / 设置持久化     │
│  · 原生手柄兜底（GameController / KeyEvent）│
└───────────────┬─────────────────────────────┘
                │ 注入 / IPC
┌───────────────▼─────────────────────────────┐
│  Input Bridge (TypeScript, 可单测)          │
│  · mapping.json（可编辑）                    │
│  · Gamepad → KeyboardEvent(keyCode)         │
│  · Virtual D-Pad / A·B → touch / key        │
└───────────────┬─────────────────────────────┘
                │ 注入 h5mota.com 文档
┌───────────────▼─────────────────────────────┐
│  mota-js (站点远程运行)                      │
│  actions.js onkeyDown/onkeyUp/ondown/onup   │
└─────────────────────────────────────────────┘
```

**硬约束重申：** Input Bridge 只翻译到引擎已有的 keyCode/触点，不绕过 route。

## 9. 触屏方案依赖壳到什么程度

| 能力 | 是否依赖壳 | 说明 |
|---|---|---|
| 引擎自带虚拟键盘/工具栏 | 否 | 页面内已有，WebView 直接可用 |
| 覆盖式虚拟摇杆/按键 | 是 | 壳层 overlay 或注入 DOM（移动主输入） |
| 安全区/刘海/手势条 | 是 | **移动优先后为 P0** |
| 外接手柄 → 虚拟键 | 是 | Input Bridge + 可能原生 |
| 横竖屏 | 部分 | 引擎已有；壳锁方向/转场 |

→ 移动优先下：**触屏是主路径，必须顺；手柄是增强路径，允许分阶段。**

## 11. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| Android WebView Gamepad 不稳 | 手柄体验差 | KeyEvent 原生转发（参考官方 Kotlin 壳） |
| WKWebView Gamepad 不完整 | iOS 手柄残缺 | 原生 GameController → 合成键事件；触屏保底 |
| Capacitor 远程 URL 非默认 | 要写加载逻辑 | 定制 WebView 插件/本地空壳页跳转 |
| 站点 CSP / 反嵌入 | 注入失败 | 实测 header；初始化脚本/用户脚本 |
| Tauri 移动踩坑（若单壳） | 移动延期 | 切回 Capacitor 移动方案 |
| 远程页改版 | 白屏 | 版本探测 + 错误页 + 注入层容错 |
| 双壳维护成本 | 工程负担 | Input Bridge/映射表只保留一份 TS |

## 13. 一句话结论

**优先级改成 Android → iOS → Win → macOS/Linux 后，主推荐从「Tauri 单壳」翻转为「Capacitor 先做 Android/iOS，Tauri 2 后补桌面」；Input Bridge 仍是共享 TS；Electron 不再适合当主壳，最多当 Windows 手柄的应急备胎。**

---

## 14. 对照：若仍是桌面优先（旧序）

| | 桌面优先（Win→Android→…） | 移动优先（Android→iOS→Win→…） |
|---|---|---|
| 主推荐 | Tauri 2 单壳 | Capacitor + Tauri 后补 |
| 备选 | Electron + Capacitor | Tauri 单壳 |
| M1 | Windows 手柄可玩 | Android 触屏可玩 |
| 最大风险 | 移动延期 | iOS/Android 手柄 |
| Electron 角色 | 桌面主力/备胎 | 仅 Windows 应急 |

同一套 **Input Bridge / 映射表** 在两种优先级下都不变——真正被优先级改变的是 **壳的主从关系与里程碑顺序**。
